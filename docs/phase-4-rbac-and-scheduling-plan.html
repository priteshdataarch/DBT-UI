DBT-UI — Phase 4 Plan

Scope: (1) Multi-user / RBAC / team management  ·  (3) Scheduled job orchestration (cron-based dbt runs)
Document type: Requirements, dependencies, architecture, execution order — for engineering and stakeholder review.

How to get one PDF: Open this file in Chrome or Edge → press Ctrl+P (Windows) or Cmd+P (Mac) → set Destination: Save as PDF → Save. That produces a single PDF containing everything below.

1. Guiding principles

  • dbt execution remains: project on disk + profiles.yml + subprocess (same as today). New layers add identity, authorization, and scheduling around that.
  • Real multi-user RBAC implies a persistent store for users, teams, roles, and optionally audit — not only HTTP headers or a shared API key.
  • Cron inside the Next.js server only is easy to ship but weak for HA and long runs; production should prefer a dedicated worker and a queue.

2. Workstream A — Multi-user / RBAC / team management

2.1 Goals

  • Multiple authenticated users (password, magic link, or SSO).
  • Teams (or organizations) with members and roles (e.g. owner, admin, developer, viewer).
  • RBAC: enforce what each role may do (view project, edit files, run dbt, git push, change target, manage schedules, invite users).
  • Optional: audit log (who did what, when).

2.2 Architecture (conceptual)

2.6 Dependencies (RBAC)

  • PostgreSQL (or equivalent) — required for durable users/teams/roles.
  • Auth.js + adapter — sessions, CSRF, OAuth callbacks.
  • HTTPS + secure cookies — production deployments.
  • Optional: email provider (Resend, SendGrid) for invites / magic links.

2.7 Execution order (RBAC)

  1. Add Postgres to local/prod topology; DATABASE_URL.
  2. Introduce Auth.js: sign-in page, session provider, protect routes.
  3. Migrate schema: users, teams, team_members.
  4. Middleware: require session for /api/* except auth callbacks and public health.
  5. Wrap APIs: /api/file, /api/dbt, /api/git, etc. — inject assertPermission.
  6. UI: login, team switcher, members/settings, disable buttons by role.
  7. Optional: audit log + admin audit viewer.

2.8 Risks (RBAC)

  • Concurrent file edits: RBAC does not replace Git; document workflow (branches, pull before push).
  • Shell / arbitrary commands: restrict to admins or disable in production.
  • Secrets: multi-tenant secrets often need a vault or per-tenant env injection — plan explicitly.

3. Workstream B — Scheduled job orchestration (cron-based dbt)

3.1 Goals

  • Define cron schedules (expression + IANA timezone).
  • Attach a dbt command (e.g. dbt run --select tag:nightly, dbt test, dbt build).
  • Execute without a browser; surface logs in UI (extend run history).
  • Optional later: Slack/email on failure.

3.2 Execution options

ApproachProsCons
In-process cron in NextFastest MVPLost on restart; poor with multiple replicas; Vercel/serverless unsuitable for long dbt.
Worker + Redis + BullMQ (recommended)Retries, persistence, HA, repeatable cronExtra services (Redis, worker container).
External (GitHub Actions, K8s CronJob, Airflow)Ops-owned reliabilityLess in-app; integrate via webhooks/API.

3.4 Minimal data model (scheduling)

EntityPurpose
scheduled_jobsteam_id, cron, timezone, enabled, command JSON (command, args, modelName, target), created_by.
job_runsjob_id, started_at, ended_at, exit_code, summary or log storage key.

Align job_runs with existing run history (file or DB) for a single timeline in the UI.

3.5 Conceptual API surface

  • POST /api/schedules — create (RBAC: admin+).
  • GET /api/schedules — list for current team.
  • PATCH /api/schedules/:id — enable/disable, edit cron/command.
  • POST /api/schedules/:id/run-now — manual trigger.
  • Worker: consumes queue; no public internet unless you add an internal trigger with shared secret.

3.6 Dependencies (scheduling)

  • Redis — job queue + repeatable jobs (BullMQ).
  • Worker service — same image as Next with different CMD, or separate Node app sharing dbt run module.
  • Shared dbt execution module — one code path used by /api/dbt and worker (arguments, cwd, env, streaming logs).
  • Cron + timezone — e.g. cron-parser or BullMQ repeat with timezone option.

3.7 Execution order (scheduling)

  1. Add Redis + worker skeleton (Docker Compose locally).
  2. Extract “run dbt subprocess + stream” into a shared library used by API and worker.
  3. Persist schedules + job_runs in App DB.
  4. Next API: CRUD + enqueue “run now”.
  5. Worker: register repeatable jobs from DB on startup + reconcile; execute dbt; write job_runs.
  6. UI: Schedules panel, link runs to history.
  7. Hardening: mutex per project for overlapping runs, timeouts, alerts.

3.8 Risks (scheduling)

  • Concurrent dbt and target/ directory — serialize or isolate worktrees.
  • Worker credentials — same as interactive dbt; document rotation.
  • Multi-tenant fairness — rate limits or per-team queues.

4. Combined phased roadmap (both workstreams)

  1. Postgres + migrations + Compose (local).
  2. Auth.js + login + session + API middleware.
  3. Teams + roles + permission checks on read APIs, then write/git/dbt.
  4. Redis + worker + shared dbt runner.
  5. Schedules CRUD + BullMQ repeat + job_runs UI.
  6. Audit + notifications (optional).

5. Phase 4 exit criteria (suggested)

  • User without role cannot run dbt or save files.
  • Team admin can invite a user; owner can remove team.
  • A schedule runs without a browser; result appears in run history.
  • Disabling a schedule stops future runs within one scheduling window.
  • Runbook documents single-replica vs multi-replica (where cron/worker runs).
