DBT-UI — Multi-warehouse adapter & production deployment

Assessment document · Not an implementation commitment · Generated for planning

1. Purpose

This document explains whether DBT-UI can be standardized to work with any dbt adapter (e.g. dbt-snowflake, dbt-redshift, dbt-bigquery, dbt-athena), what is already generic, what is vendor-specific, and what a production-ready, Dockerized architecture would require.

2. Executive summary

dbt CLI execution (run, test, compile, docs, etc.) — Already adapter-agnostic. dbt reads profiles.yml and uses whichever adapter is installed in the environment. No code change is strictly required to switch from Athena to Snowflake for dbt commands, as long as the container or host has the right pip install dbt-<adapter> and valid profiles.

SQL Editor & “Preview data” (live SELECT against the warehouse) — Currently coupled to AWS Athena in a typical implementation (e.g. AWS SDK, Glue catalog, S3 query output). Making this work for Snowflake/Redshift/BigQuery is possible but requires new backend modules per engine (or a thin “query gateway” service), plus secrets and network design.

Production Docker — Possible and standard: Next.js standalone image, mount or copy the dbt project, inject secrets via env/secrets manager, health checks, non-root user optional hardening. The prior exploratory Dockerfile/compose work was reverted per request; this document describes the target shape without shipping those files.

4. Feasibility matrix

CapabilityAny dbt adapter?Notes
Run / test / compile / docs / lineage from manifest Yes Uses dbt subprocess + project files. Adapter is selected by profiles.yml + installed Python packages.
Environment switcher (--target) Yes dbt-native; profiles define outputs.
AI / RAG using catalog.json Yes Adapter-agnostic metadata from dbt.
Ad-hoc SQL editor + result grid Athena today Needs per-warehouse driver/API (Snowflake connector, JDBC pool, BigQuery client, etc.).
Preview data (compiled model → SELECT) Athena today Same as above; must compile first in all cases.
Single Docker image: Node + dbt + adapter Yes Build ARG for pip install dbt-snowflake (etc.). Image size grows with native deps.
Secrets in production Yes Use K8s secrets, AWS Secrets Manager, env from orchestrator — never bake into image.

5. What “standardize for any dbt” would require (engineering plan)

Phase A — Low effort (already aligned)

  • Keep all dbt invocations via CLI with explicit --project-dir / --profiles-dir / --target.
  • Document supported adapters and a single DBT_ADAPTER_PACKAGE (or multi-stage image) for Docker builds.
  • UI copy: refer to “warehouse” where behavior is not Athena-specific.

Phase B — Medium effort (optional live SQL)

  • Introduce QUERY_ENGINE=athena|snowflake|none (example) in server config.
  • Implement /api/query and /api/preview behind a strategy interface: AthenaRunner, SnowflakeRunner, …
  • Map env vars per engine (Snowflake: account, user, private key or password, role, warehouse, database, schema).
  • Security: parameterized execution only, read-only roles for preview, timeouts, row limits.

Phase C — Production hardening

  • Next.js output: 'standalone' for minimal runtime image.
  • Non-root user, read-only root FS where possible, tmpfs for caches.
  • Health endpoint (e.g. GET /api/health) and readiness checks.
  • Mount dbt project as volume for live edits, or bake for immutable deploys.
  • Reverse proxy (TLS), rate limits, auth in front of the studio if exposed beyond VPN.

6. Risks and constraints

  • Credentials: The server runs dbt and optional queries; it must hold warehouse credentials in memory or delegate to OIDC/workload identity — design carefully.
  • Shell / arbitrary commands: If exposed, treat as admin-only or disable in production.
  • Adapter-specific SQL: dbt models are still warehouse SQL dialects; the IDE does not magically translate dialects.
  • Licensing: Some JDBC/ODBC drivers have license terms separate from dbt.

7. Conclusion

Using DBT-UI with any dbt adapter for core dbt workflows is already possible with the right Python environment and profiles.yml. Fully adapter-neutral “live SQL” and preview is possible but not automatic: it is a deliberate second product surface (multi-driver query layer) on top of the existing dbt-centric design.

Docker / Kubernetes production deployment is standard practice and feasible; the main decisions are image layout (dbt in-image vs sidecar), secret injection, and whether the SQL editor is enabled for your warehouse.
